# Install k3d on Fedora over Tailscale

## Step 1: Install Latest k3d on Fedora

Log into your Fedora machine (`ssh root@<TAILSCALE_IP>`) and run the official installation script:

```bash
curl -s https://raw.githubusercontent.com/k3d-io/k3d/main/install.sh | bash
```

Verify the installation and check the version:

```bash
k3d --version
```

## Step 2: Ensure Fedora’s Firewall Allows Tailscale Traffic

Fedora's firewalld blocks incoming external traffic to container runtimes by default. Run this on your Fedora machine to ensure your Macbook can communicate with the API server over Tailscale:

```bash
sudo firewall-cmd --zone=trusted --add-interface=tailscale0 --permanent
sudo firewall-cmd --reload
```

## Step 3: Spin Up Your Isolated Cluster

Still on the Fedora machine, run the following command to create the cluster:

```bash
k3d cluster create my-labs \
  --api-port <TAILSCALE_IP>:6443 \
  --k3s-arg "--tls-san=<TAILSCALE_IP>@server:*"
```

### Why these parameters?

- `--api-port <TAILSCALE_IP>:6443` explicitly binds the Kubernetes control plane interface only to your Tailscale IP on port 6443.
- `--k3s-arg "--tls-san=..."` forces K3s to generate an SSL certificate valid for that Tailscale IP, avoiding "invalid certificate" validation errors on your Mac.

## Step 4: Configure Your Macbook

Now, shift over to your Macbook's terminal to establish the remote connection.

### 1. Download the config over Tailscale

Run this single pipeline command to grab the generated kubeconfig directly from your remote machine:

```bash
ssh root@<TAILSCALE_IP> "k3d kubeconfig get my-labs" > ~/.kube/remote-k8s.yaml
```

### 2. Update the Target Endpoint IP

The configuration generated by k3d defaults to localhost since it assumed it was being queried locally. Fix it on your Macbook by replacing `0.0.0.0` or `127.0.0.1` with your remote Tailscale IP:

```bash
# Using sed to quickly switch the target server address
sed -i '' 's/0.0.0.0/<TAILSCALE_IP>/g' ~/.kube/remote-k8s.yaml
sed -i '' 's/127.0.0.1/<TAILSCALE_IP>/g' ~/.kube/remote-k8s.yaml
```

### 3. Switch Context and Test Your Lab

Tell your Macbook terminal session to use this configuration file:

```bash
export KUBECONFIG=~/.kube/remote-k8s.yaml
```

Test your direct control plane connection:

```bash
kubectl get nodes
```

You should see your k3d node sitting cleanly in a `Ready` state. Your `helm` and `kubectl` commands will now seamlessly deploy to the Fedora container sandbox over Tailscale without messing up any of your other non-Kubernetes Docker containers.

## Directing Lab Deployments to the Remote Cluster

To run any of the `kubectl` or `helm` commands in the other pattern directories (e.g., `adapter`, `ambassador`, `gateway-api`, etc.) against this remote `k3d` cluster, simply ensure that your current terminal session has the `KUBECONFIG` environment variable exported:

```bash
export KUBECONFIG=~/.kube/remote-k8s.yaml
```

Once exported, all standard Kubernetes tooling (`kubectl`, `helm`, `kustomize`, etc.) executed from that terminal will target your remote Fedora machine over Tailscale.

## Troubleshooting & Common Scenarios

### Scenario 1: What happens if the Docker Daemon restarts?
*(e.g., Fedora laptop reboots, or you run `systemctl restart docker`)*

By default, `k3d` configures its containers with a restart policy of `unless-stopped`.

- **The Cluster:** When the Docker daemon comes back online, the `k3d` containers will automatically boot back up. Your cluster state, deployments, and namespaces are entirely preserved (they live in Docker volumes managed by `k3d`).
- **Your Macbook:** You do not need to change anything. Once the containers finish booting (usually takes about 10–20 seconds), your Macbook's `kubectl` commands will just start working again.

### Scenario 2: What happens if you delete and recreate the cluster?

If you run `k3d cluster delete my-labs` and then recreate it, your Macbook will lose connection—even if you use the exact same cluster name.

#### Why does it break?
- **The TLS Certificate changes:** Every time a new cluster is born, it generates brand new internal cryptographic keys and TLS certificates. Your Macbook's existing `remote-k8s.yaml` expects the old certificate. If you try to run `kubectl`, you'll get an `x509: certificate signed by unknown authority` error.
- **The Cluster Token changes:** The internal security token used to authenticate your administrative context changes entirely.

#### How to handle recreations / new names:
Whenever you tear down a cluster and spin up a new one (whether it has the same name or a brand-new name like `prod-test`), you need to re-run the pipeline on your Macbook to pull the fresh config:

1. **Pull the new config and fix the IP:**
   ```bash
   # Pull the new file (change "my-labs" if you named the cluster differently)
   ssh root@<TAILSCALE_IP> "k3d kubeconfig get my-labs" > ~/.kube/remote-k8s.yaml

   # Fix the local loopback target back to your Tailscale IP
   sed -i '' 's/0.0.0.0/<TAILSCALE_IP>/g' ~/.kube/remote-k8s.yaml
   sed -i '' 's/127.0.0.1/<TAILSCALE_IP>/g' ~/.kube/remote-k8s.yaml
   ```

2. **Point to it (if it's a new terminal window) and test:**
   ```bash
   export KUBECONFIG=~/.kube/remote-k8s.yaml
   kubectl get nodes
   ```

## Pro-Tip: Managing Multiple Active Clusters

If you eventually want to run two different sandboxes at the same time on that remote machine (e.g., `labs-alpha` and `labs-beta`), they just cannot share the same Tailscale host port.

You would spin up the second one on a different API port (e.g., `6444`):

```bash
k3d cluster create labs-beta \
  --api-port <TAILSCALE_IP>:6444 \
  --k3s-arg "--tls-san=<TAILSCALE_IP>@server:*"
```

You can then merge both configurations together on your Macbook to switch contexts seamlessly using `kubectl config use-context`.
