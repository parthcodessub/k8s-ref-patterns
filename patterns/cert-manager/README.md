# Cert-Manager: The Kubernetes Machine Identity System

## 🚀 Overview
At its core, **cert-manager** is the de facto Kubernetes-native X.509 certificate controller. It treats certificates as first-class citizens (Custom Resources), automating their entire lifecycle: requesting, issuing, renewing, and revoking.

For a **Lead/Staff Engineer**, cert-manager is not just about getting a green lock on a website; it is the **policy enforcement point** for Machine Identity across a distributed system.

---

## 🧠 Core Architecture & Concepts

Cert-manager is built on a controller pattern. It watches for `Certificate` resources and attempts to fulfill them by communicating with an `Issuer`.

### Key Custom Resource Definitions (CRDs)
| Resource | Scope | Description |
| :--- | :--- | :--- |
| **Issuer** | Namespaced | Represents a Certificate Authority (CA) available only within a specific namespace. Good for tenant isolation. |
| **ClusterIssuer** | Cluster-wide | A CA available to all namespaces. Common for shared "Let's Encrypt" accounts or a central Vault path. |
| **Certificate** | Namespaced | The human-readable intent: "I want a cert for `api.example.com` valid for 90 days." |
| **CertificateRequest** | Namespaced | The actual CSR (Certificate Signing Request) generated by cert-manager. |
| **ACME Order** | Namespaced | (Specific to ACME) Tracks the progress of an HTTP or DNS challenge. |

### The Issuance Flow
```mermaid
graph TD
    A[User/Ingress] -->|Creates| B(Certificate CR)
    B -->|Triggers| C{Cert-Manager Controller}
    C -->|Generates Key Pair| D[Secret (Private Key)]
    C -->|Creates| E(CertificateRequest)
    E -->|Sent to| F[Issuer / ClusterIssuer]
    
    subgraph "External World"
    F -->|ACME Challenge| G[Let's Encrypt / Google CAS]
    F -->|RPC Call| H[HashiCorp Vault / Venafi]
    end

    G -->|Signed Cert| C
    H -->|Signed Cert| C
    C -->|Updates| B
    C -->|Saves Cert| I[Kubernetes Secret]
```

## 🏢 Enterprise Use Cases (Lead Level Patterns)
In large organizations, you rarely just "use Let's Encrypt." You integrate with established Trust Models.

### 1. Centralized PKI Integration
Enterprises treat PKI as a managed service. Cert-manager acts as the "glue" layer or specific **Registration Authority (RA)**. It uses specialized "Issuers" to talk to these systems.

*   **HashiCorp Vault (`VaultIssuer`)**: Cert-manager authenticates to Vault (via K8s ServiceAccount) and requests certs from a specific PKI secret engine path. This keeps the Root CA highly secured in Vault.
*   **AWS Private CA (`AWSPrivateCAIssuer`)**: Connects K8s directly to AWS ACM Private CA. Useful if you want AWS to manage the CRL (Certificate Revocation List) and HS availability.
*   **Venafi**: The "Gold Standard" for Global 5000 machine identity. Cert-manager talks to the TPP (Trust Protection Platform) to enforce globally consistent policy.

### 2. Compliance & Short-Lived Certificates
To minimize blast radius, high-security environments use extremely short-lived certificates (e.g., **1 hour** or **24 hours**).
*   **The Problem**: A human cannot rotate certs daily.
*   ** The Solution**: Cert-manager monitors the `RenewBefore` annotation. For a 24h cert, it might renew at hour 16 automatically.
*   **Audit**: Every `CertificateRequest` is a Kubernetes object that can be logged, audited, and piped to SIEM tools.

### 3. Policy as Code (OPA/Kyverno)
You can use admission controllers to enforce strict policies on `Certificate` objects:
*   *Prevent issuance of Wildcard certs (`*.com`).*
*   *Enforce specific DNS zones.*
*   *Mandate specific `Issuer` usage (e.g., Prod apps must use `prod-issuer`).*

## 🔒 Deep Dive: mTLS, Istio & Identity

### 1. The Core Bridge: `istio-csr`
By default, Istio's control plane (`istiod`) acts as its own Certificate Authority (CA). In an enterprise setting, you often want to replace this with cert-manager so you can use your corporate PKI (like Vault or AWS Private CA).

`istio-csr` is an agent that sits in front of cert-manager. It exposes a gRPC interface that looks exactly like Istio's built-in CA.

### 2. Sidecar vs. Ambient Mesh
| Feature | Istio Sidecar (Envoy) | Istio Ambient (ztunnel) |
| :--- | :--- | :--- |
| **Requestor** | `istio-agent` (in Sidecar) | `ztunnel` (DaemonSet) |
| **Identity Scope** | 1 Cert per Pod | Many Certs per Node (Multi-tenant) |
| **Flow** | Pod -> istio-csr -> cert-manager | ztunnel -> istio-csr -> cert-manager |

### 3. The Certificate Lifecycle (Step-by-Step)
1.  **Request**: Pod starts. `istio-agent` generates a Private Key & CSR in memory.
2.  **Sign**: CSR sent to `istio-csr` -> converts to K8s `CertificateRequest` -> Cert-Manager -> Vault.
3.  **Issue**: Signed Cert returns.
4.  **Mount**: `istio-csr` returns cert to agent. Agent pushes to Envoy via SDS (Secret Discovery Service).
    *   **Critical**: The Private Key never leaves the pod's memory and is never written to disk.

### 4. Gateway API vs. Pod Identity
*Understanding the "Edge" vs "Internal" trust boundaries.*

| Component | Purpose | Cert Type | Manager |
| :--- | :--- | :--- | :--- |
| **Gateway (Edge)** | Public Traffic (Ingress) | Public (Let's Encrypt) | Standard `Certificate` Resource (Static Secret) |
| **Sidecar (Mesh)** | Internal Traffic (East-West) | Private (Internal PKI) | Dynamic (SDS / Ephemeral) |

#### Gateway API Configuration
Cert-manager integrates natively with the Gateway API via annotations:
```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  gatewayClassName: istio
  listeners:
  - name: https
    hostname: "api.example.com"
    port: 443
    protocol: HTTPS
    tls:
      mode: Terminate
      certificateRefs:
      - name: api-example-com-tls
### 5. Detailed Flow: Ambient Mesh (HBONE)
In Ambient Mesh, there are no sidecars. A `ztunnel` runs on every node.
1.  **Identity Discovery**: `ztunnel` detects a new pod (`orders-svc`) on its node.
2.  **Impersonation**: `ztunnel` requests a cert for `orders-svc` from `istiod` (which delegates to `istio-csr`).
3.  **Verification**: `istio-csr` validates that *this specific ztunnel* is allowed to host `orders-svc` (based on node affinity/SA token).
4.  **Issuance**: Cert-manager signs it; `ztunnel` holds it in memory.
5.  **Multi-Node Identity**: If `orders-svc` runs on 5 nodes, there are 5 different certificates for the same identity. This limits the "Blast Radius" of a compromised node.

### 6. Deep Dive: SPIFFE & Authorization
How do we replace "RBAC" with "Identity"?

**The SPIFFE ID**:
A Universal Resource Identifier (URI) embedded in the X.509 Certificate's **SAN** (Subject Alternative Name).
`spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>`
*Example*: `spiffe://cluster.local/ns/prod/sa/orders`

**AuthorizationPolicy (The "Firewall")**:
We don't check IP addresses. We check the SPIFFE ID.

```yaml
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-orders-to-payment
  namespace: finance-prod
spec:
  selector:
    matchLabels:
      app: payment-svc  # Apply to Payment Server
  action: ALLOW
  rules:
  - from:
    - source:
        # Check the certificate SAN
        principals: ["cluster.local/ns/orders-prod/sa/orders-svc-sa"]
    to:
    - operation:
        methods: ["POST"]
        paths: ["/v1/charge"]
```

### 5. Conceptual: Service Account vs. Certificate
*The most common interview distinction.*

*   **Service Account**: The **Identity** (Who you are). A K8s logical construct.
*   **Certificate**: The **Credential** (ID Card). A cryptographic proof of that identity.

You need both: Use the Certificate to establish the encrypted tunnel (Authentication), then use the Service Account attributes to enforce RBAC (Authorization).

## 🛠️ Implementation Strategy: ACME Challenges
When using ACME (Let's Encrypt), you must prove you own the domain.

### 1. HTTP-01 Challenge
*   **How**: Cert-manager spins up a temporary Pod and creating a temporary Ingress routing `/.well-known/acme-challenge/XYZ` to it.
*   **Pros**: Simple, works with any DNS provider.
*   **Cons**:
    *   Requires a public IP (or valid Ingress path).
    *   **Does NOT support Wildcard certificates.**

### 2. DNS-01 Challenge
*   **How**: Cert-manager uses a Webhook to create a `TXT` record in your DNS provider (Route53, Cloudflare, etc.).
*   **Pros**:
    *   Supports **Wildcard Certificates**.
    *   Works in private networks (as long as cert-manager can talk to the DNS API).
*   **Cons**: Slower (DNS propagation), requires API credentials for DNS provider (risk of credential leakage).

## 📋 Cheat Sheet: Certificate Types

| Type | Trusted By | Use Case |
| :--- | :--- | :--- |
| **Self-Signed** | Nobody (except the issuer) | Bootstrapping, local dev, or the very first Root CA. **Avoid in Prod.** |
| **Internal CA** | The Cluster Only | Webhooks, internal APIs. Root CA is managed by cert-manager inside the cluster. |
| **Enterprise CA** | The Whole Organization | Ingress, Public APIs, interacting with legacy systems. Backed by Vault/Venafi. |
| **Public Acme** | The World | Public facing websites (Let's Encrypt). |

## 👨‍💻 Hands-On: The "Standard" Pattern (ACME)

This is the Bread-and-Butter configuration for 90% of Kubernetes clusters using Let's Encrypt.

### 1. The ClusterIssuer (The Authority)
This tells cert-manager *how* to talk to Let's Encrypt.
```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    # You must replace this email
    email: user@example.com
    server: https://acme-v02.api.letsencrypt.org/directory
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
    # Use HTTP-01 by default
    - http01:
        ingress:
          class: nginx
```

### 2. The Ingress Shim (The Shortcut)
Instead of manually creating a `Certificate` object, you just annotate your Ingress. Cert-manager watches Ingresses and automatically creates the Certificate for you.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: kuard
  annotations:
    # This annotation triggers cert-manager
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - example.com
    secretName: quickstart-example-tls # <--- Cert-manager will populate this Secret
  rules:
  - host: example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: kuard
            port:
              number: 80
```

## ⚠️ Troubleshooting & Gotchas

1.  **"Challenge Failed"**:
    *   Check `kubectl describe challenge`.
    *   **HTTP-01**: Is a firewall blocking port 80? Is the Ingress Class correct?
    *   **DNS-01**: Are the IAM permissions for Route53 correct? (Needs `ChangeResourceRecordSets`).

2.  **Rate Limits**:
    *   Let's Encrypt Staging vs Prod. **Always** test with Staging first. If you fail Prod validation 5 times, you are blocked for an hour.

3.  **Secret Rotation**:
    *   Cert-manager updates the **Secret**. It does *not* automatically restart your application pods.
    *   If your app loads certs only at startup, it will eventually fail.
    *   **Fix**: Use `reloader` (stakater/Reloader) annotation to bounce pods when the Secret changes.






## 👨‍💻 Hands-On: Enterprise PKI & Istio Ambient
*Instead of letting Istio be its own CA (the default), we will create a "Corporate Root" inside cert-manager and force Istio's Ambient Mesh to trust it.*

### Lab Architecture
1.  **Corporate Root CA**: A self-signed cert-manager Issuer (simulating an offline Root).
2.  **Mesh Intermediate CA**: A CA signed by the Root, derived specifically for this cluster.
3.  **istio-csr**: The gRPC agent that intercepts Istio's CSRs and sends them to cert-manager.
4.  **Istio Ambient**: The "sidecar-less" mesh that uses these identities for its ztunnels.

### Step 1: Install Cert-Manager
```bash
helm repo add jetstack https://charts.jetstack.io --force-update
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --set crds.enabled=true
```

### Step 2: Create the "Enterprise" PKI
*This mimics a company like "MyCorp" giving you an intermediate CA for your cluster.*

```yaml
# 1. Create a Self-Signed Issuer to act as the "External" Corporate Root
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: selfsigned-root-issuer
  namespace: cert-manager
spec:
  selfSigned: {}
---
# 2. Generate the "Corporate Root" Certificate
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: corporate-root-ca
  namespace: cert-manager
spec:
  isCA: true
  commonName: corporate-root-ca
  secretName: corporate-root-ca-secret
  issuerRef:
    name: selfsigned-root-issuer
    kind: Issuer
---
# 3. Create the "Mesh CA" Issuer that uses that Root
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: mesh-ca-issuer
  namespace: cert-manager
spec:
  ca:
    secretName: corporate-root-ca-secret
```

### Step 3: Install istio-csr
This is the "bridge" that tells the mesh: "Don't sign your own certs; ask me, and I'll ask cert-manager."

```bash
helm install cert-manager-istio-csr jetstack/cert-manager-istio-csr \
  --namespace cert-manager \
  --set "app.certmanager.issuer.name=mesh-ca-issuer" \
  --set "app.certmanager.issuer.kind=Issuer" \
  --set "app.server.caTrustedNodeAccounts=istio-system/ztunnel" # Crucial for Ambient!
```

> **Why `caTrustedNodeAccounts`?**
> This flag is the "Gatekeeper". In Ambient Mesh, the `ztunnel` is shared (one per node). It must request certificates for *other* pods. By setting this, you tell `istio-csr`: *"I trust the ztunnel ServiceAccount to impersonate other identities."*

### Step 4: Install Istio Ambient (CNI Configuration)
```bash
# Install Gateway API CRDs (required)
kubectl get crd gateways.gateway.networking.k8s.io || \
  kubectl kustomize "github.com/kubernetes-sigs/gateway-api/config/crd?ref=v1.1.0" | kubectl apply -f -

# Install Istio Profile (Adjusted for K3s/Rancher pathways)
istioctl install -y --set profile=ambient \
  --set values.cni.cniBinDir=/var/lib/rancher/k3s/data/cni \
  --set values.cni.cniConfDir=/var/lib/rancher/k3s/agent/etc/cni/net.d \
  --set values.global.caAddress=cert-manager-istio-csr.cert-manager.svc:443
```

### Step 5: Verify Identity
Deploy a workload and check who signed its certificate.

```bash
kubectl create ns lab-mesh
kubectl label namespace lab-mesh istio.io/dataplane-mode=ambient
kubectl apply -f https://raw.githubusercontent.com/istio/istio/master/samples/sleep/sleep.yaml -n lab-mesh
```

**Check the `ztunnel` certs:**
```bash
# Get the ztunnel on the same node
istioctl zc certificates ztunnel-xxxxx -n istio-system
```
*   **Success**: The issuer is `corporate-root-ca`.
*   **Fail**: The issuer is `O=cluster.local` (Default Istio CA).
*   **Empty List**: Use the `sleep` pod to make a request; `ztunnel` loads certs lazily (on-demand).

## ⚠️ Deep Dive: Troubleshooting CNI & Mesh

### 1. The "CNI Chaining" Problem
In k3s, Flannel (Primary CNI) sets up the network. Istio CNI (Secondary) needs to "chain" onto it to inject iptables rules.
*   **Failure Mode**: Istio CNI pod stays in `Init/Waiting`.
*   **Cause**: It's looking for CNI configs in `/etc/cni/net.d`, but k3s puts them in `/var/lib/rancher/k3s/agent/etc/cni/net.d`.
*   **Fix**: Explicitly set `values.cni.cniConfDir` during helm/istioctl install.

### 2. Lead Architecture: The API Aggregation Global Blockage
*Q: Can one broken app break the entire cluster's operations? Yes.*

**The Scenario**: You try to delete a namespace (`kubectl delete ns lab-mesh`), and it hangs in `Terminating` forever. You also notice the KEDA namespace is stuck.

**The Root Cause (The "Discovery" Bottleneck)**:
1.  **Deletion Sweep**: When deleting a NS, the Namespace Controller must "discover" all resources inside it to finalize them.
2.  **Aggregation Layer**: It asks the API Server for a list of all resource types.
3.  **Broken Pipe**: The API Server checks registered extension APIs. If you have an `APIService` (like KEDA metrics v1beta1) but the backing KEDA pods are dead/deleted, the request **hangs or returns 503**.
4.  **Global Deadlock**: The Discovery Client fails to get a "complete map" of the cluster. The Namespace Controller, being cautious, **refuses to process deletions** for *any* namespace because it can't guarantee there aren't hidden resources managed by that broken API.

**Lead Takeaway**:
*   Always uninstall high-level Operators (Helm delete) *before* deleting their namespace.
*   If stuck, check strict `APIService` health: `kubectl get apiservice`. Delete any that are `False/Unavailable`.
